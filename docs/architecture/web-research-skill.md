# 联网研究技能：触发边界与工具架构

本文是设计约定，**当前程序尚未自动联网搜索**。这里的“技能”指 ZhuangFY 的对话流程能力，不等同于 Codex 技能文件；“工具”指可执行的检索或读取操作；“插件”指为工具提供具体服务的适配器。

## 先定义三层

```text
QQ / 桌面文字 / 语音
    ↓ 同一 ConversationService（后续迁移）
web_research 技能：判断是否查、查什么、何时停止
    ↓ ToolRegistry：启用状态、输入校验、次数和时限
web.search / web.fetch：只读工具
    ↓ 可替换适配器：DeepSeek Search & Fetch / SearXNG / 其他服务
证据（标题、URL、摘要、日期、取得时间）→ 回复模型 → 带来源的答复
```

目前 `SenseVoice/dashboard.py` 的“插件管理”是本机组件的状态页，尚未提供工具注册、授权和调用。`SenseVoice/chat_worker.py` 与 `SenseVoice/qq_bridge.py` 也各自协调对话。因此，搜索应接在将来共享的会话服务中，而非让 QQ 与桌面各写一套搜索判断。人格包负责说话方式，不负责决定是否发起网络请求。

## 什么时候查

| 本轮请求 | 决定 | 例子 |
| --- | --- | --- |
| 明确要求搜索、核实、查看某个网页 | 查 | “帮我查一下今天的公告” |
| 答案依赖当前日期、价格、版本、政策、天气、活动或最新进展 | 查 | “这个模型现在支持哪些接口？” |
| 用户要来源，或者问题很具体而模型没有可靠依据 | 查 | “这条说法出自哪份官方文档？” |
| 有足够的本地对话、记忆或用户给出的材料可回答 | 不查 | “我之前说过喜欢什么？” |
| 主观交流、情绪陪伴、图片分享或不要求外部事实的创作 | 不查 | “看看这张图的感觉” |
| 要求代用户发消息、修改账户或执行网页操作 | 不由搜索工具执行 | “查完就替我提交申请” |

分三步判定：程序先识别明确指令和明显时效性；边界模糊时才让规划模型给出 `search / no_search / ask_clarification`、理由及最多两条查询；执行器再检查工具是否启用、渠道预算、查询内容和授权。**模型说“搜索”不等于已经获得无限制的网络访问。**对于“今年哪款更好”这类混合问题，可先查可核验的规格与现状，再说明偏好判断属于建议。没有查到证据时明确说无法核实，不把模型旧知识包装成最新消息。

## 查什么，以及怎样使用结果

1. 查询只包含必要的实体、事实问题和时间范围。优先检索官方文档、原始公告、论文或直接来源，再用其他来源交叉核对。不要把整段 QQ 聊天、长期记忆、QQ 号、联系人信息、图片或语音转写原文直接拼进查询；用户明确要查自己提供的特定内容时，也先裁剪到完成任务所需的部分。
2. 首版每轮最多两次搜索、读取最多两篇页面。常规问题以 3–5 条结果为候选；只在摘要不足或来源需要核实时读取页面全文。语音渠道应有更短的等待预算，并告知用户正在查询。
3. 每条证据保留 `title`、`url`、`snippet/content`、`published_at`（若有）、`retrieved_at`。区分页面发布日期与事件发生日期；日期缺失时不推断为“今天”。多来源冲突时说明分歧。
4. 搜索结果和网页文字是**外部资料，不是指令**。忽略其中要求泄露密钥、改变人格、再次调用工具或执行本地命令的内容。将截断后的证据交给回复模型，要求有依据的事实附 URL；QQ 文字可附链接，语音朗读只讲结论和简短来源名，具体链接留在文字记录。
5. 默认不把网页内容写入“用户个人记忆”。用户说过的偏好与外部网页事实不能混为一条记忆。运行监控记录查询理由、查询词、来源和耗时；不记录密钥或网页全文。

## 首个适配器与替换边界

可以先试 **DeepSeek 官方 Search & Fetch API**：项目已有 DeepSeek 模型供应商与本机密钥管理，官方接口分别返回搜索结果与单页内容。它和 Chat Completions 的 `tool_calls` 是两回事：模型只提出调用请求，实际联网仍由应用执行。适配器以后可换成 SearXNG（实例须开启 JSON 输出）或其他检索服务，而 `web_research` 的判定与证据结构不变。

参考：[DeepSeek Search & Fetch](https://api-docs.deepseek.com/guides/search/)、[DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)、[SearXNG Search API](https://docs.searxng.org/dev/search_api.html)、[MCP 的 Prompts / Resources / Tools 区分](https://modelcontextprotocol.io/specification/draft/server/index)。接口能力、额度和计费在接入时重新核对，不把当前网页内容当成永久配置。

## 实施顺序

1. 建立 `ToolDecision`、`ToolResult` 与只读 `ToolRegistry`。先用离线样例测试“应该查 / 不该查”、敏感查询裁剪和预算；不接真实搜索。QQ、桌面和语音都调用同一个决策入口。
2. 接入一个 `web.search` + `web.fetch` 适配器和本机配置；用公开、非私人测试词验证搜索结果、超时、空结果和来源链接。工具失败不阻塞普通对话，但回复不得伪称已核实。
3. 在插件管理页显示联网技能启用状态、供应商、当次调用次数和失败原因，并提供总开关；默认关闭。之后再考虑多供应商备援。
4. 等只读工具稳定，再评估日历、提醒等会改变外部状态的工具。它们必须有独立权限与确认流程，不能因为“搜索技能已启用”就自动获得执行权。

验收用例至少包括：问今天的版本触发搜索；问庄方宜如何称呼用户不搜索；发一张图片不搜索；给出指定网页时只读该页；搜索结果夹带“忽略原指令”时不执行；搜索超时后不编造实时结论；QQ 与桌面在相同问题上使用同一判定规则。
